## 1. 직전 차단 문제는 실제로 해결됐다

직전 보고서의 차단 사유는 `backend/app/main.py`의 SPA fallback 경로 탈출이었다.
구현 담당자의 수정을 **믿지 않고 다시 공격해 확인했다.**

HTTP 클라이언트(.NET `Invoke-WebRequest`, httpx)는 요청을 보내기 전에 URL의 `..`를
스스로 정규화해 버리므로, 그 도구로는 진짜 공격을 재현할 수 없다. 그래서 **raw socket으로
요청 줄을 직접 써서** 43종을 보냈다(자체 기동 서버 port 8811).

| 분류 | 시도한 경로 | 결과 |
|---|---|---|
| 직전 결함 그대로 | `/../../.env`, `/../../../.env`, `/%2e%2e/%2e%2e/.env`, `/..%2f..%2f.env`, `/%2e%2e%2f%2e%2e%2f.env`, `/assets/../../../.env` | 전부 차단 |
| 다른 파일 | `/../../backend/app/main.py`, `/../../.gitignore`, `/../../README.md`, `/../../.git/config`, `/../../backend/.env.example`, `/../../start-local.cmd`, `/../../frontend/vite.config.ts`, `/../../보도자료작성요령교육.pdf` | 전부 차단 |
| 검사원이 추가로 고안한 우회 | 백슬래시 `/..\..\.env`·`/..%5c..%5c.env`, 이중 인코딩 `/%252e%252e/...`, `/....//....//.env`, `/..;/..;/.env`, 절대경로 `/C:/policy_agent/.env`·`/C:\policy_agent\.env`, UNC `//127.0.0.1/C$/...`, 오버롱 UTF-8 `/..%c0%af..%c0%af.env`, 전각 슬래시 `/..%ef%bc%8f...`, `%u2215`, NUL `/../../.env%00.html`, 후행 점·공백 `/../../.env.`·`/../../.env `, Windows ADS `/../../.env::$DATA`·`/index.html::$DATA`, 부분 인코딩 `/%2e%2e/%2e%2e/%2e%65%6e%76` | 전부 차단 |
| `/assets` mount 탈출 | `/assets/%2e%2e/%2e%2e/%2e%2e/.env`, `/assets/..%2f..%2f..%2f.env`, `/assets/..\..\..\.env`, `/assets/../index.html` | 전부 404 |

판정 방법은 `.env`를 **열지 않는다**. 응답 본문이 `frontend/dist/index.html`
446 bytes와 SHA-256(`5056b7ea…`)까지 같은지, 그리고 응답 길이가 디스크의
`.env` 378 bytes·`README.md` 290,119 bytes·`main.py` 4,319 bytes와 일치하는지만 비교했다.
**일치 0건, 유출 0건.**

검사가 무조건 통과하는 위양성이 아님을 대조군으로 확인했다.
`/assets/index-DntkmZcf.js`는 206,868 bytes로 정상 서빙되고, `/api/health`·`/api/contract`는
자기 JSON을 돌려준다. 즉 "무엇을 요청해도 index.html"이 아니라 **경계 밖만 되돌려 보낸다.**

`backend/app/main.py`의 수정 자체도 읽어서 확인했다. `(FRONTEND_DIST / path).resolve()`가
`FRONTEND_DIST.resolve()`의 하위인지 `is_relative_to`로 보고, `OSError`·`ValueError`도
잡아 첫 화면으로 되돌린다. `resolve()`가 심볼릭 링크와 Windows 8.3 단축 이름까지 풀기 때문에
링크를 이용한 우회도 같은 검사에 걸린다.

**결론: 직전 차단 문제는 해결됐다.**

## 2. 새로 발견한 차단 문제 — `D1G-02`

### 증상

문서화된 실행법이 동작하지 않는다.

```
> cmd.exe /c C:\policy_agent\start-local.cmd
'indstr' is not recognized as an internal or external command,
operable program or batch file.
exit code 255
```

- 한글 배너조차 출력되지 않는다. 전체 출력이 97 bytes다.
- 8765 포트에 listener **0건** — 서버가 아예 뜨지 않는다.
- 브라우저도 열리지 않고, `.local-server.pid`도 만들어지지 않는다.
- **4회 재현**했다.

```
> cmd.exe /c C:\policy_agent\stop-local.cmd
'…트로' is not recognized as an internal or external command,
'…록된' is not recognized as an internal or external command,
'…되어' is not recognized as an internal or external command,
  [멈춤] 서버를 종료하지 못했습니다. 작업 관리자에서 확인해 주세요.
'…를' is not recognized as an internal or external command,
```

`.local-server.pid`가 없는 상태였으므로 "이 스크립트로 시작한 서버가 없습니다"가 나와야 하는데,
파싱이 어긋나 **틀린 분기로 들어가 잘못된 실패 안내를 출력한다.**

### 원인 (대조 실험으로 확정)

두 `.cmd` 파일이 **LF만으로 저장**되어 있다.

| 파일 | 크기 | CRLF | LF |
|---|---|---|---|
| `start-local.cmd` | 2,618 bytes | **0** | 76 |
| `stop-local.cmd` | 1,132 bytes | **0** | 40 |

`cmd.exe`는 배치 파일을 바이트 오프셋으로 따라가며 읽는데, `chcp 65001`로 코드 페이지를 바꾼 뒤
여러 바이트 한글이 섞인 파일을 LF만으로 저장하면 오프셋 추적이 어긋나 **명령이 잘린 채 실행된다.**
`findstr` → `indstr`가 그 결과다.

`start-local.cmd`의 앞 25줄을 **바이트 그대로** 복사해 LF본과 CRLF본을 만들어 실행했다.

| 판본 | 결과 |
|---|---|
| LF본 (배포된 파일과 같은 바이트) | `'lth'`, `'erver.pid"'`, `'---…'`, `'…이고'` 등 **5건**의 잘린 명령 오류, 한글 배너 깨짐 |
| CRLF본 (**줄바꿈만** 다름) | 한글 배너 정상 출력, 오류 **0건**, `PORT-FREE` → `REACHED-END` 정상 도달 |

내용이 아니라 **줄바꿈이 원인**이다.

`.gitattributes`의 `* -text`가 LF 바이트를 그대로 고정하므로 **어느 checkout에서도 재현된다.**
(그 설정 자체는 `test_sets/CHECKSUMS.sha256`과 `PG-001` 해시를 지키려는 것이므로,
`.cmd`만 CRLF로 고정하는 방식이 필요하다.)

### 부수 피해

`start-local.cmd` 실행 중 프로젝트 루트에 0바이트 파일 `같은`이 생성됐다.
REM 주석의 `-> 같은 주소로 브라우저 열기` 조각이 잘려 리디렉션으로 실행된 것으로 보인다.
검사원이 제거해 작업 트리를 원래대로 되돌렸다.

### 왜 계약 위반인가

- `D1G-02`의 PASS 증거는 "**문서화된 실행법으로** `127.0.0.1` 한 주소의 `/api/health`가 200을
  반환하고 첫 화면이 로드되며, 자신이 시작한 프로세스만 정상 종료"다.
- README §3.7의 1일차 종료 조건은 "**실행 바로가기에서 브라우저가 열리고**"다.
- README §3.8은 "일반 사용자는 명령어를 입력하지 않고 로컬 실행 바로가기 하나를 누른 뒤"라고
  못 박았고, §3.9는 `start-local.cmd`·`stop-local.cmd`를 그 진입점으로 지정한다.

서버 코드는 정상이다. `python -m uvicorn app.main:app`으로 직접 띄우면
`/api/health` 200, 첫 화면 200(`#root` 포함), 종료 뒤 잔여 listener 0건으로 잘 동작한다.
**깨진 것은 서버가 아니라 사용자가 실제로 쓰는 실행 진입점이다.**

### script가 이것을 놓친 이유

`scripts/verify-day1.ps1`은 `D1G-02`에서 `start-local.cmd`/`stop-local.cmd`를
**한 번도 실행하지 않고** uvicorn을 직접 띄운다. 그래서 이 결함이 1차·2차 검증에서
연속으로 PASS를 통과했다. 고칠 때 script에도 실행 바로가기 자체를 돌려 보는 단계를 넣어야 한다.

## 3. 강화된 script의 탐지 능력 평가

새로 넣은 검사가 형식적인지 확인하려고, **일부러 취약하게 만든 미끼 서버**(수정 전
SPA fallback을 그대로 복원, 가짜 `.env`·가짜 소스 파일을 둔 별도 디렉터리)를 만들어
script와 시험이 그 서버를 잡아내는지 측정했다. 제품 코드는 건드리지 않았다.

| 검사 | 탐지 | 놓침 |
|---|---|---|
| `verify-day1.ps1`의 경로 탈출 6종 | **2/6** — `/%2e%2e/%2e%2e/.env`, `/..%2f..%2f.env` | `/../../.env`, `/../../.gitignore`, `/../../backend/app/main.py`, `/assets/../../../.env` |
| `tests/test_harness_flow.py`의 회귀 시험 7종 | **3/7** — `%2e%2e` 2종 + `/C:/Windows/win.ini` | `..` 4종 |

놓친 이유는 같다. .NET `System.Uri`와 httpx가 **요청을 보내기 전에** 점 세그먼트를 정규화해
서버에는 `..`가 도착하지 않는다. 즉 목록의 3분의 2는 위안용이다.

다만 **결함 자체는 잡힌다.** 퍼센트 인코딩 2종이 실제로 미끼 서버의 유출을 탐지했으므로,
이 부류의 회귀는 다시 들어오면 걸린다. 그래서 `D1G-07`은 FAIL이 아니라 PASS이고,
탐지 목록의 허수는 경고로 남긴다. 진짜 방어를 원하면 raw socket 요청을 한 건이라도 넣으면 된다.

강화된 나머지 항목은 실질적이다.

- `.env` 읽기: `Fail-Check $c7` — 경고가 아닌 차단 (코드에서 확인)
- 잔여 포트: `Fail-Check $c2` — 경고가 아닌 차단 (코드에서 확인)
- 빌드 결과물 없음: `Fail-Check $c7` — dist가 없으면 bundle 검사를 못 한 것으로 보고 차단
- 쿠키 없는 요청: 403이 아닌 오류는 통과로 보지 않도록 상태 코드를 확인하게 바뀜

## 4. 멱등 계약 (README 664줄) 확인

raw socket으로 실제 요청을 보내 확인했다.

| 요청 | 기대 | 실제 |
|---|---|---|
| 1회차 (키 K, 내용 P) | 202 + 새 Run | `202 RUN-1FD11A0C74C8` |
| 2회차 (키 K, **같은** 내용 P) | 최초 HTTP 상태·응답 재사용 | `202`, **같은 run_id** |
| 3회차 (키 K, **다른** purpose) | `409 IDEMPOTENCY_KEY_REUSED` | `409 IDEMPOTENCY_KEY_REUSED` |
| 4회차 (키 K, **다른** sources) | `409 IDEMPOTENCY_KEY_REUSED` | `409 IDEMPOTENCY_KEY_REUSED` |
| 5회차 (다른 키, 진행 중 Run 존재) | 거부 | `409 RUN_ALREADY_EXISTS` |

`payload_hash()`가 `client_request_id`만 빼고 정규화 JSON을 해시하므로 `purpose`뿐 아니라
`sources` 변경도 정확히 잡힌다. **README 664줄대로 구현됐다.**

남은 차이 하나는 경고로 남긴다. 멱등 메타데이터가 `Run` 객체에만 있어서,
**`DELETE` 뒤에는 같은 키 + 다른 내용이 `202`로 통과해 새 Run이 만들어졌다.**
README §2.13의 "멱등 메타데이터는 원문 없이 2시간 보관"은 아직 구현되지 않았다.
1일차 차단 사유는 아니지만 2일차 이후로 넘어간다.

## 7. 고치는 방향 (검사원은 코드를 고치지 않는다)

1. `start-local.cmd`와 `stop-local.cmd`를 **CRLF로 저장**한다.
2. `.gitattributes`에 `*.cmd text eol=crlf`(또는 동등한 고정)를 더해 checkout에서도 유지되게 한다.
   `* -text`는 checksum 고정 목적이므로 `.cmd`만 예외로 두는 형태가 안전하다.
3. 고친 뒤 실제로 두 번 눌러 확인한다. 브라우저가 열리는지, `.local-server.pid`가 생기는지,
   `stop-local.cmd`가 **그 PID만** 종료하고 다른 포트 프로세스는 건드리지 않는지.
   (CRLF 대조 실험은 앞 25줄까지만 확인했으므로 나머지 흐름은 새로 검증해야 한다.)
4. `scripts/verify-day1.ps1`의 `D1G-02`에 `start-local.cmd`/`stop-local.cmd`를 실제로 실행하는
   단계를 넣는다. 넣지 않으면 같은 결함이 세 번째로 통과한다.
5. (권장) 경로 탈출 검사에 raw socket 요청을 한 건 넣어, 클라이언트가 URL을 정규화해
   검사가 헛돌지 않게 한다.
6. (2일차 이후) 멱등 메타데이터를 Run 수명과 분리해 2시간 보관한다.
7. (2일차 이후) localhost Host 검사를 조회 API에도 적용할지 정한다.
